# Privacy-Preserving Filesharing Track: Testnet v0.4

## 1. [Use Service Discovery](https://github.com/logos-storage/logos-storage-pm/issues/32)

Storage currently requires its mixnet and DHT-proxy pools to be manually
configured, which rules out user participation. We want to integrate Anon. Comms
[service discovery
implementation](https://lip.logos.co/anoncomms/raw/logos-service-discovery.html)
so that users can contribute to both pools (and perhaps to NAT relay and AutoNAT
pools too).

## 2. [Block Protocol and Mix Transport Optimizations](https://github.com/logos-storage/logos-storage-pm/issues/33)

For v0.3, we've created an initial implementation of [a libp2p Mix
transport](https://github.com/logos-storage/libp2p-mix-transport) and made our
existing block protocol work on top of it, mostly unmodified. This is about:

1. tailoring block protocol parameters so as to bring it closer to the maximum
   performance that mix transport can provide;
1. improving efficiency of the Mix transport itself.

## 3. [Use Mix Transport for DHT Proxies](https://github.com/logos-storage/logos-storage-pm/issues/34)

We're currently using a legacy request/reply mechanism for routing DHT queries
over Mix. With Mix transport, this is no longer necessary. We want to retire
this and use Mix transport for everything instead.

## 4. [Evaluate Mix Transport and Private Downloads Over an RLN](https://github.com/logos-storage/logos-storage-pm/issues/35)

We currently run our own mixnet, and do not have RLN enabled. We expect RLN to
impact things broadly - performance should degrade significantly, resource usage
should go up significantly, and the onboarding will become a lot more complex
with RLN registration and the need to run a blockchain node alongside storage.
Before we understand the amount of work required to get this working properly,
we need to evaluate it. 

Assuming that evaluation turns out positive, we might optionally deliver (5) 
as part of testnet v0.4.

## 6. [Naming Service](https://github.com/logos-storage/logos-storage-pm/issues/38)

Content-addressed file storage means addressing is linked to content, but often
one wants to provide a stable identifier to content that can change. We intend
to deliver a flavour of [IPNS](https://specs.ipfs.tech/ipns) in which
self-verifiable name records can be used to point to different CIDs over time,
effectively allowing addressable mutable content.

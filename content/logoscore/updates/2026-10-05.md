# Logoscore Weekly Update — 2026-10-05

## Highlights

- **The 0.3.0 catalog was cut in about 48 hours.** It ships the LEZ 0.3.0 stack, libp2p 1.1.0, storage 3.0.2 and blockchain-ui 0.3.1. A stale-checkout bump rolled ten pins back, and they were restored within six hours [logos-modules-release#78](https://github.com/logos-co/logos-modules-release/pull/78), [#85](https://github.com/logos-co/logos-modules-release/pull/85)
- **Installs now offer optional dependencies**, the same way in Basecamp, PMUI and logosctl. If one fails, the install carries on [logos-package-downloader#44](https://github.com/logos-co/logos-package-downloader/pull/44), [logos-basecamp#452](https://github.com/logos-co/logos-basecamp/pull/452), [logos-logoscore-cli#160](https://github.com/logos-co/logos-logoscore-cli/pull/160)
- **Calling a method a module doesn't have is now an error.** It used to return `ok` with a zero. Every SDK and the Qt glue now answer `unknown_method` [logos-cpp-sdk#178](https://github.com/logos-co/logos-cpp-sdk/pull/178), [logos-rust-sdk#72](https://github.com/logos-co/logos-rust-sdk/pull/72), [logos-plugin-qt#56](https://github.com/logos-co/logos-plugin-qt/pull/56)
- **Packages can be downloaded over Logos Storage.** A new setting lets the user allow any transport, Storage only, or HTTP only [logos-package-downloader-module#32](https://github.com/logos-co/logos-package-downloader-module/pull/32), [logos-package-downloader#42](https://github.com/logos-co/logos-package-downloader/pull/42), [logos-basecamp#416](https://github.com/logos-co/logos-basecamp/pull/416)
- **A reloaded module can no longer hand a call another call's old result.** Call ids are now unique per instance [logos-plugin-qt#58](https://github.com/logos-co/logos-plugin-qt/pull/58), [logos-protocol#108](https://github.com/logos-co/logos-protocol/pull/108)
- **All 13 Basecamp UI doctests now run on Windows**, and they leave no processes behind [logos-basecamp#470](https://github.com/logos-co/logos-basecamp/pull/470), [#471](https://github.com/logos-co/logos-basecamp/pull/471)
- **Reinstalled apps open without restarting Basecamp.** View backends are reached through dynamic replicas [logos-view-module-runtime#40](https://github.com/logos-co/logos-view-module-runtime/pull/40)
- **Blockchain UI now reads its mining state from the node**, counts claims made while the app was closed, and uses Quick start mining defaults a desktop can spare [logos-blockchain-ui#85](https://github.com/logos-blockchain/logos-blockchain-ui/pull/85), [#86](https://github.com/logos-blockchain/logos-blockchain-ui/pull/86), [#91](https://github.com/logos-blockchain/logos-blockchain-ui/pull/91)
- **Loading an LGX package takes about a fifth of the memory it did**: 754 MiB → 154 MiB on a 150 MiB package [logos-package#44](https://github.com/logos-co/logos-package/pull/44)
- **libp2p's `flake.lock` went from 450k lines to 17k** [logos-libp2p-module#111](https://github.com/logos-co/logos-libp2p-module/pull/111)

### Blockchain UI — mining state from the node, and the claims it missed

- **Mining state is now read from the node.** Mining had been a fire-and-forget toggle with no readback, so the view showed what it last requested. It went wrong whenever the node started or stopped mining on its own. `pow_status` is now read on every status poll. It is not tied to the claimable-tickets timer, because that timer runs only while the app believes mining is on, which is exactly the belief the readback exists to correct. Views bind to `miningActive`, the node's answer whenever there is one. The old request flag survives only as a fallback for a module without `pow_status`, and to keep the button responsive until the next poll. Auto-claim is resolved the same way. That includes the node's own reason for standing auto-claim down: every claim target has reached its threshold [logos-blockchain-ui#85](https://github.com/logos-blockchain/logos-blockchain-ui/pull/85)
- **No `pow_*` call is made before the chain has first been online.** Until then the node's PoW service doesn't read its inbox, and the module waits on it with no timeout on its own thread. An early call therefore stalled every other call and every event, blocks included. The gate is latched once per run, and all PoW state is cleared when the node leaves Running [logos-blockchain-ui#85](https://github.com/logos-blockchain/logos-blockchain-ui/pull/85)
- **Claims made while the app was closed are now counted.** A catch-up reads `get_blocks` from the last scanned slot up to LIB, 2,000 slots per status poll. That is about 50 blocks: few enough not to stall the poll, and enough that a full backfill takes minutes, not hours. When a block holding our claims has no successor in the window, the window doubles, up to 64,000 slots. Raw blocks carry neither a header id nor transaction hashes. Ids are therefore recovered from the next block's `parent_block`, and claims are keyed by the beneficiary `pk` the reward note is minted to. A reply that isn't a JSON array counts as a failure, not an empty window, so a range is never skipped for good. Results go into a `ClaimLedger` that is saved to disk with a write throttle. Until the scan has reached back to genesis, the Earned tiles say which period they cover [logos-blockchain-ui#86](https://github.com/logos-blockchain/logos-blockchain-ui/pull/86)
- **Quick start mines with desktop defaults.** Quick start never shows the PoW form, so the node used to mine with its own defaults: every CPU, 4 searches per block, and a 300 s claim period. Quick start now writes 1 thread, 1 search per block and a 10 s claim period, and Advanced's form starts from the same values. The setting is relabelled "Parallel ticket searches per block", because it does not cap how many tickets a block can earn [logos-blockchain-ui#91](https://github.com/logos-blockchain/logos-blockchain-ui/pull/91)
- **Claims in flight, and who counts as funded.** The dashboard now tells claims sent apart from claims settling ("3 sent · 2 settling", or "sent, not seen yet"). The funded-wallet check now accepts any tracked account holding tokens, not only the one with the `leader_funding` role [logos-blockchain-ui#84](https://github.com/logos-blockchain/logos-blockchain-ui/pull/84)
- **Shipped** as 0.3.0, again as 0.3.0 with the CPU% fix, and as 0.3.1 with the new defaults [logos-modules-release#81](https://github.com/logos-co/logos-modules-release/pull/81), [#82](https://github.com/logos-co/logos-modules-release/pull/82), [#95](https://github.com/logos-co/logos-modules-release/pull/95)

### Optional dependencies, chosen at install time

- **The resolver offers optional dependencies and returns the full graph it chose.** Each optional dependency is returned as an offer. An offer lists the catalog versions it permits after filtering by version range, artifact and signer pins, download source, and whether its required packages can be installed. The returned graph includes packages that are already installed, so a frontend can re-resolve to find nested optionals and drop branches the user deselected [logos-package-downloader#44](https://github.com/logos-co/logos-package-downloader/pull/44)
- **Offers now agree with the required plan.** Several mismatches were reproduced before being fixed. A dependency already scheduled at a newer version by another package overwrote the plan's manifest. An optional needing `D ^2` was offered while the plan installed `D 1.x`. An offer was marked unavailable when only its newest release failed. Offers are no longer built for packages the plan already requires, which took a large synthetic resolve from **~1.5 s to ~0.14 s** with identical output [logos-package-downloader#45](https://github.com/logos-co/logos-package-downloader/pull/45)
- **Installed optionals can now be upgraded or downgraded.** When the caller supplied the installed set, the resolver had dropped installed optionals from the offers entirely. The default request now pins the installed release, so leaving an offer untouched changes nothing. An installed optional that was never published, such as the embedded `modules_state`, shows as installed-only instead of unavailable [logos-package-downloader#46](https://github.com/logos-co/logos-package-downloader/pull/46), [#47](https://github.com/logos-co/logos-package-downloader/pull/47), [logos-basecamp#455](https://github.com/logos-co/logos-basecamp/pull/455)
- **Basecamp's install and upgrade dialogs.** Optional dependencies get the same row as required ones, with a version selector that changes the version and its artifact hash together. A follow-up fixed four problems: an unrelated dialog could cancel PMUI's install gate, leaving every later install refused as busy; the upgrade cascade showed checkboxes that froze Continue; a version pick could loop into an unresolvable selection; and a failed re-resolve emptied the list, so the change that caused it could not be undone [logos-basecamp#452](https://github.com/logos-co/logos-basecamp/pull/452), [#453](https://github.com/logos-co/logos-basecamp/pull/453)
- **PMUI now installs the optional dependencies the shell approved.** It had been discarding the shell's response and installing only the original set. With the new `InstallSequence`, a failed optional row is marked Failed and the batch continues; a failed required row still stops it [logos-package-manager-ui#89](https://github.com/logos-co/logos-package-manager-ui/pull/89), [#90](https://github.com/logos-co/logos-package-manager-ui/pull/90)
- **logosctl `apply()` had three bugs.** `package upgrade` uninstalled every named package but downloaded only the ones that had changed, so a package that was already current was removed and never reinstalled. A failing optional aborted the run before the restarts; it is now reported as `skipped_optional`. And `--no-deps` installed the whole transitive closure. Four of the seven new tests fail if the fixes are reverted [logos-logoscore-cli#160](https://github.com/logos-co/logos-logoscore-cli/pull/160), [#161](https://github.com/logos-co/logos-logoscore-cli/pull/161), [#162](https://github.com/logos-co/logos-logoscore-cli/pull/162)
- **Docs and repins.** The developer guide documents the default selections, the RLN → LEZ RLN chain, and branch pruning [logos-package-downloader-module#46](https://github.com/logos-co/logos-package-downloader-module/pull/46), [#47](https://github.com/logos-co/logos-package-downloader-module/pull/47), [#48](https://github.com/logos-co/logos-package-downloader-module/pull/48), [logos-tutorial#104](https://github.com/logos-co/logos-tutorial/pull/104), [#105](https://github.com/logos-co/logos-tutorial/pull/105), [#106](https://github.com/logos-co/logos-tutorial/pull/106)

### Where packages come from — the Storage fetcher, the download source, and a downloader that starts on request

- **The downloader owns its Storage node.** It starts the node with the config the Storage UI shares, and doctests download by CID from a local provider. A follow-up made unloading safe: new calls are refused, pending storage waits are cancelled, and an in-flight HTTPS download is aborted through the library's new cancel API, which also removes the partial file. The subscription to `storage_module` is made lazily, so hosts without that module get no retry warnings [logos-package-downloader-module#32](https://github.com/logos-co/logos-package-downloader-module/pull/32), [#44](https://github.com/logos-co/logos-package-downloader-module/pull/44), [logos-package-downloader#43](https://github.com/logos-co/logos-package-downloader/pull/43), [logos-logoscore-cli#115](https://github.com/logos-co/logos-logoscore-cli/pull/115)
- **How the download source decides availability.** Availability is computed each time the catalog is read and never stored in the cached index. A download without a pinned version takes the newest release the setting can serve; a pinned download fails and says why. All three frontends show the result: in PMUI the Not available reason updates as the Version picker moves, Basecamp's selector restores the previous value if a change is refused, and logosctl has `catalog source`. The downloader gained 12 new tests, and reverting each guard fails its own test [logos-package-downloader#42](https://github.com/logos-co/logos-package-downloader/pull/42), [logos-package-downloader-module#45](https://github.com/logos-co/logos-package-downloader-module/pull/45), [logos-package-manager-ui#86](https://github.com/logos-co/logos-package-manager-ui/pull/86), [logos-basecamp#438](https://github.com/logos-co/logos-basecamp/pull/438), [logos-logoscore-cli#147](https://github.com/logos-co/logos-logoscore-cli/pull/147)
- **The downloader now starts only when asked, and the catalog is fetched only when something reads it.** Loading the downloader had started a Storage node in every host, including a `logosctl` daemon. It now exposes `start()`, `stop()`, `getState()` and `stateChanged`. Basecamp no longer fetches the catalog at launch: App Manager fetches it when it opens, and Welcome search on the first query [logos-package-downloader-module#50](https://github.com/logos-co/logos-package-downloader-module/pull/50), [logos-package-manager-ui#93](https://github.com/logos-co/logos-package-manager-ui/pull/93), [logos-basecamp#469](https://github.com/logos-co/logos-basecamp/pull/469), [logos-logoscore-cli#173](https://github.com/logos-co/logos-logoscore-cli/pull/173)
- **Both hosts now start the downloader at load again, because the lazy start broke stopping the node from the Storage UI.** `start()` brings up a node if none is running, so a node the user had stopped came back the moment App Manager opened. Basecamp and the logosctl daemon now start the downloader as soon as it loads. Basecamp also clears its started flag when the downloader's subscription is lost, so calls to a reloaded instance are no longer refused. `basecamp-storage-download` passes **30/30** and `logosctl-storage-install` **38/38** [logos-basecamp#474](https://github.com/logos-co/logos-basecamp/pull/474), [logos-logoscore-cli#175](https://github.com/logos-co/logos-logoscore-cli/pull/175), [logos-package-downloader-module#54](https://github.com/logos-co/logos-package-downloader-module/pull/54)
- **The downloader doctests no longer touch the public network.** The default-node spec had failed on both OSes since 10-01: `KadDHT.start` waits on a bootstrap refresh against the public `logos.test` fleet, and took 70 s locally even with the fleet up. The spec now uses an offline config. The storage provider is pinned to a revision that builds, because logos-storage-nim's default branch broke on 10-03 [logos-package-downloader-module#51](https://github.com/logos-co/logos-package-downloader-module/pull/51), [#52](https://github.com/logos-co/logos-package-downloader-module/pull/52), [logos-logoscore-cli#174](https://github.com/logos-co/logos-logoscore-cli/pull/174)
- **LGX streaming load reached every consumer through relocks**: lgpm, the PM module, PMUI, Basecamp and logosctl. The relocks also shrank logosctl's lock from 2,218 to 1,458 nodes over the week [logos-package-downloader#48](https://github.com/logos-co/logos-package-downloader/pull/48), [logos-package-manager#47](https://github.com/logos-co/logos-package-manager/pull/47), [logos-package-manager-module#76](https://github.com/logos-co/logos-package-manager-module/pull/76), [logos-package-downloader-module#49](https://github.com/logos-co/logos-package-downloader-module/pull/49), [logos-package-manager-ui#91](https://github.com/logos-co/logos-package-manager-ui/pull/91), [logos-basecamp#456](https://github.com/logos-co/logos-basecamp/pull/456), [#461](https://github.com/logos-co/logos-basecamp/pull/461), [logos-logoscore-cli#169](https://github.com/logos-co/logos-logoscore-cli/pull/169), [#170](https://github.com/logos-co/logos-logoscore-cli/pull/170), [nix-bundle-lgx#19](https://github.com/logos-co/nix-bundle-lgx/pull/19), [nix-bundle-logos-module-install#10](https://github.com/logos-co/nix-bundle-logos-module-install/pull/10)

### Upgrades and reinstalls that replace only what changed

- **Embedded packages can be upgraded.** The upgrade keeps the bundled copy, which is read-only, and installs the replacement into the user directory. Uninstalling the user copy brings the embedded one back. App Manager now checks a package's `installType` again before removing anything, because its cached map can be incomplete during a refresh [logos-package-manager-module#75](https://github.com/logos-co/logos-package-manager-module/pull/75), [logos-package-manager#45](https://github.com/logos-co/logos-package-manager/pull/45), [logos-package-manager-ui#88](https://github.com/logos-co/logos-package-manager-ui/pull/88), [logos-basecamp#447](https://github.com/logos-co/logos-basecamp/pull/447), [logos-logoscore-cli#158](https://github.com/logos-co/logos-logoscore-cli/pull/158), [logos-liblogos#236](https://github.com/logos-co/logos-liblogos/pull/236)
- **Reinstalling one component no longer refetches the whole app.** The skip check for packages already on disk ran on the download's results instead of before the request; it now compares version and `rootHash` first. A doctest counts `.lgx` requests in a local server's access log: three on the first install, **one** on the reinstall. The same PR unloads an app's running modules before any of their dependencies is replaced. Previously an upgrade succeeded while the old module kept running [logos-basecamp#444](https://github.com/logos-co/logos-basecamp/pull/444)
- **Installing an app whose dependency only Basecamp ships.** With the built-in catalog disabled, a dependency that only Basecamp bundles is in no enabled catalog, and the resolve failed with `no candidate matches` even though the installed copy satisfied the range. The preview now retries with that installed package [logos-basecamp#472](https://github.com/logos-co/logos-basecamp/pull/472)
- **logosctl now names the running dependents an install stops.** Reinstalling `calc_slow` silently left `calc_fanout` unloaded. The install plan now lists `stopped_dependents` with a `module load` hint for each one. They are deliberately not restarted [logos-logoscore-cli#166](https://github.com/logos-co/logos-logoscore-cli/pull/166)
- **Packages this host cannot install are hidden by default.** On Windows most catalog rows could only say Not available. PMUI and App Manager now hide them, and a filter shows them again. That filter combines with the install-state tabs. Grid tiles also give names the cell's full width [logos-package-manager-ui#87](https://github.com/logos-co/logos-package-manager-ui/pull/87), [logos-basecamp#445](https://github.com/logos-co/logos-basecamp/pull/445), [#446](https://github.com/logos-co/logos-basecamp/pull/446)
- **Distribution fixes.** A detached `logosctl daemon` started from an AppImage relaunched the copy inside `/tmp/.mount_*`, so `storage_module` and `package_downloader` crashed with signal 7 once the outer runtime exited. It now relaunches the outer AppImage. lgpm releases now include a Windows zip [logos-logoscore-cli#159](https://github.com/logos-co/logos-logoscore-cli/pull/159), [logos-package-manager#46](https://github.com/logos-co/logos-package-manager/pull/46)

### Protocol and SDK correctness

- **A blocking call to a module that isn't loaded now fails in 1 s, not 20 s.** `requestObject()` knew nothing was listening and still waited the full budget. It now waits at most 1 s for a listener; a module that is listening keeps the full budget. The two absent-module tests went from about 20 s to about 1.1 s [logos-protocol#105](https://github.com/logos-co/logos-protocol/pull/105)

### Process lifetime and runtime races

- **A module that calls out from its own init no longer has those calls refused.** liblogos told capability_module about the new token only after the child reported its plugin loaded, so the module's first calls failed with "auth token not recognized". That is how `package_downloader` could read `is_ready("storage_module")` as false. The token is now registered before the child receives it, and a failed load revokes it. Integration passes 49/49 [logos-liblogos#237](https://github.com/logos-co/logos-liblogos/pull/237)
- **A memory-corruption bug present since intents first landed was crashing Basecamp.** `IntentBroker::dispatchTo` held a `QHash` iterator across `deliverRequest`, which can answer the intent synchronously and erase the record. One byte was then written through the dead iterator, showing up as `double free or corruption` and as a SIGSEGV during QML garbage collection. The broker now looks the record up again after any call that can re-enter it. Replaying deep-link launches went from 5 core dumps in ~12 launches to 0 in 180 [logos-basecamp#463](https://github.com/logos-co/logos-basecamp/pull/463)
- **logosctl fixes.** `watch` now exits with `NO_DAEMON` about 1 s after the daemon stops; before, it was still running 31 s later and never exited. `daemon stop` no longer aborts when the process is reaped between opening and reading `/proc/<pid>/stat`, a race that had failed a tutorial CI run. `modules_state` and `capability_module` are now reported as installed, so a dry-run install of `eth_wallet_ui` no longer fails with `no candidate matches` [logos-logoscore-cli#164](https://github.com/logos-co/logos-logoscore-cli/pull/164), [#171](https://github.com/logos-co/logos-logoscore-cli/pull/171), [#165](https://github.com/logos-co/logos-logoscore-cli/pull/165)
- **The module inspector's CPU usage is accurate again**, after a `process-stats` pin fix [logos-liblogos#239](https://github.com/logos-co/logos-liblogos/pull/239), [logos-basecamp#460](https://github.com/logos-co/logos-basecamp/pull/460)
